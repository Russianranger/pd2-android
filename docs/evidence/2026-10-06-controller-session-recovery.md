## Distinct follow-up experiments

The current transport experiment intentionally changes one controller subsystem. The following candidates were researched without replacing the accepted PE drivers or repeating failed reconnect tests:

- **XInput return diagnostics:** pinned [ntdll/relay.c](https://github.com/brunodev85/wine-9.2-custom/blob/a4ef2bf8963fe4bfab390eebf73336364ce209bc/dlls/ntdll/relay.c) can filter builtin exports and print scalar returns. A future explicitly diagnostic `xinput1_4.XInputGetState`/GetStateEx relay would distinguish disconnected status from cached-state success without dereferencing controls; freshness and game acceptance still require separate evidence. WoW64 operation/overhead still needs qualification. Filters are global HKCU `Software\\Wine\\Debug` and loaded once per process; any implementation must journal exact previous registry presence/type/value, write only after full cleanup, and restore only unchanged owned values. A separate helper loading its own XInput DLL would compete for 7949 and is unsuitable.
- **Reader liveness:** pinned [ntdll socket.c](https://github.com/brunodev85/wine-9.2-custom/blob/a4ef2bf8963fe4bfab390eebf73336364ce209bc/dlls/ntdll/unix/socket.c) retries EINTR and warns on other non-WOULDBLOCK receive failures. Existing warn logging already covers those failures without broad Winsock TRACE. No such warning appears in the retained gameplay head/tail, which cannot establish absence over the whole attempt. The actual trace shows the donor reader thread created as `wine_xinput_controller_read`. The pinned native thread layer writes this description into Linux comm, truncated to 15 characters. A bounded known-thread count could distinguish a socket from a surviving reader, with unreadable proc fields remaining unknown. A guarded reader restart/timeout would require a separately qualified XInput DLL revision.
- **One HID source for both APIs:** [official Wine 9.2 XInput](https://github.com/wine-mirror/wine/blob/wine-9.2/dlls/xinput1_3/main.c) enumerates HID gamepad/joystick interfaces and reads a descriptor compatible with this producer. An opt-in matching 32-bit PE module could remove independent UDP XInput lifetime. Its analog trigger scaling and Y-axis inversion differ from the accepted donor policy; a future build must preserve the accepted digital-trigger semantics or explicitly qualify the affected controls. Exact exports/imports/WoW64 ABI, verified backup and rollback must be established first; bundling it now would confound the UID result.
- **Wine HIDclass cancellation/removal races:** upstream [a2479097](https://github.com/wine-mirror/wine/commit/a2479097ab8a453eb3cc3d39504d1970388cf222) (2024-08-07) unifies queue/removal locks and [4ba2f77f](https://github.com/wine-mirror/wine/commit/4ba2f77fb6714d98285d8a07a8b6fbf85c0a9080) (2025-09-09) corrects an early IRP-cancellation test. Both fixes are absent from the pinned custom `hidclass.sys/device.c`. A third focused fix, [b2ce2222](https://github.com/wine-mirror/wine/commit/b2ce22225dd184aa4b3025acf19c17a59aa37302) (2025-03-19), completes pending winexinput reads on actual REMOVE_DEVICE; the pinned [winexinput source](https://github.com/brunodev85/wine-9.2-custom/blob/a4ef2bf8963fe4bfab390eebf73336364ce209bc/dlls/winexinput.sys/main.c) only does so on SURPRISE_REMOVAL. They are credible later backport candidates if removal stalls or a fresh acknowledged HID still fails. The current log does not establish a cancelled IRP or causally link those locks to `sync_cs`. The retained driver releases its own lock before lower-driver calls/IRP completion, and ntoskrnl releases `sync_cs` before the actual wait; no lock cycle is demonstrated. No PE driver patch is included.

Official SDL2 RawInput was inspected at [4c2d9014](https://github.com/libsdl-org/SDL/blob/4c2d9014afda49553c76f7045529207bb593f9b5/src/joystick/windows/SDL_rawinputjoystick.c), and SDL3 at [2296712f](https://github.com/libsdl-org/SDL/blob/2296712f9f7ab4cb00678b55352c5bc9f43321ee/src/joystick/windows/SDL_rawinputjoystick.c). ## Physical interpretation

Use [the focused 0.1.16 test](../TESTING.md), without preparing runtime or re-importing. Export after Save/Quit failure before running the experiment; test the fresh identity once and export its outcome. Then save/quit, completely Stop client, and Play again within the same Android process.

If Stop/Play restores Native, accept that full-session repair separately from Save/Quit. If identity recovery works, retain its explicit experimental status until repeatability is demonstrated. If it fails with a fresh acknowledged device and ongoing state/report counts, investigate game/XInput ownership next rather than repeating the older reconnect. If cleanup remains refused, compare verified residuals, unknown identity fields and independent port outcomes; do not reset the import or runtime to erase that evidence.

Compare progress only while Native's input gate is open. The ACK heartbeat comes from the actual Winebus wait loop, not an independent health worker. Advancing Android event and successful non-neutral send counts with a stalled heartbeat and backend state/report counters would support investigation of the Winebus/PE cancellation path. Advancing fresh-UID backend state/report counts while gameplay remains unresponsive would instead move the next experiment toward XInput/API returns or game ownership. Neither pattern establishes the final cause alone. A successful legacy XInput bind is particularly weak liveness evidence: the pinned donor enables SO_REUSEADDR on UDP 7949, and its reader can exit while initialized/connected state remains.
